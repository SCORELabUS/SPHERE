# SPHERE Agents

## Project Structure

- **api/** — Express + MongoDB + Redis backend (TypeScript)
- **frontend/** — React + Vite + TailwindCSS v4 frontend
- Package manager: **pnpm** (not npm/yarn)

## Developer Commands

```bash
pnpm run install    # Install dependencies for both packages
pnpm run dev        # Run API + Vite dev servers concurrently (from root)
pnpm run dev:setup  # Run MongoDB and Redis containers locally with Docker Compose. Also seeds MongoDB with test data. It must be run BEFORE dev commands.
pnpm run test       # Run API tests (vitest) then reseed MongoDB
pnpm run build      # Build both frontend and api
```

## Running Single Test / Package

```bash
cd api && npx vitest --run --test-name-pattern "<pattern>"
```

## Important Quirks

- `test` script runs `seed:mongo-local:small` **after** tests to reset state
- Tests run sequentially (`fileParallelism: false` in vitest.config.ts)
- API entry point: `api/src/main/backend.ts`
- Migrations auto-run via `npx migrate up` in `dev:api` script
- API uses `ts-migrate-mongoose` for MongoDB migrations
- `api/scripts/link-zip-uploads-to-collections.ts` links pricings of ZIP uploads made before the bulk upload stored their collection: a dry run by default (`npx tsx --tsconfig tsconfig.json scripts/link-zip-uploads-to-collections.ts` from `api/`), `--apply` links only the unambiguous ones. It is not a migration that runs by itself.
- The API is rate limited (`api/src/main/middlewares/RateLimitMiddleware.ts`), with counters in Redis: 300 requests every 10 seconds per user or, without one, per IP (`RATE_LIMIT_MAX_REQUESTS`, `RATE_LIMIT_WINDOW_SECONDS`), and 10 every 5 minutes per address and account on login, registration and password reset (`AUTH_RATE_LIMIT_MAX_REQUESTS`, `AUTH_RATE_LIMIT_WINDOW_SECONDS`). A value of 0 turns a limiter off. Both are off under Vitest unless set explicitly, and requests go through if Redis is down.
- Pricings use optimistic concurrency. `GET /pricings/{org}/{slug}` returns `ETag: "<pricingId>.<revision>"`; the revision lives on `PricingIdentity` and moves on with every write to any version (`refreshIdentities` in `PricingMongoose.ts`, plus `PricingRepository.create`/`bumpRevisions` where no middleware runs). `PUT`/`DELETE` on the pricing or a version and `POST` of a version accept `If-Match`: `PricingRepository.claimRevision` checks it and claims the revision in one conditional update before the write, so a stale tag gets 412 and changes nothing. The revision also moves with private versions, so only callers who may read the private versions (`_canSeePrivateVersions`) get an `ETag`, and for anyone else no tag matches (only `*`). Without `If-Match` writes behave as before (ORBIT never sends one); `PRICING_REQUIRE_IF_MATCH=true` makes it required on `PUT`/`DELETE` (428), off by default. Revision-bearing reads and the full pricing-service mutation (including writes without If-Match) share a queue by pricingId in `utils/pricing-revision-lock.ts`, so a GET cannot pair a claimed revision with content that has not been written. This queue is shared across service instances in the current single API process; before running multiple API processes, replace it with cross-process coordination or transactions. The guard is always released on errors.
- NGINX also limits each IP (`nginx/*/nginx.conf`): 50 requests/s with bursts of 100 on `/api/v1`, and 20/s with bursts of 40 on `/harvey-api`, answering 429. It is the barrier against floods; the per-user limits are the API's.

## ORBIT assistant

- Lives in `api/src/main/services/orbit/` and is served under `/api/v1/orbit/**`. The model only reads (query tools) and proposes plans; `OrbitPlanService` validates them by code and `OrbitExecutorService` applies a confirmed plan with the user's own permissions, re-checked per step.
- Configured with `ORBIT_OPENAI_API_KEY` (falls back to `HARVEY_API_KEY`, then `OPENAI_API_KEY`), `ORBIT_OPENAI_MODEL` (default `gpt-5-nano`) and optionally `ORBIT_OPENAI_BASE_URL`. Without a key, `GET /orbit/status` reports `available: false` and messages answer 503.
- In production ORBIT uses HARVEY's OpenAI key (see the docker-compose files), so both share its rate limits and spending. `ORBIT_MAX_MESSAGES_PER_MINUTE` (default 20) caps the messages of all ORBIT users together to leave room for HARVEY; each user is also limited to 30 messages every 10 minutes and to `ORBIT_MESSAGES_PER_HOUR` (10) messages an hour, shown as `maxOrbitMessages` in SPHERE's pricing (`frontend/public/pricing/SPHERE.yml`). Past the hourly limit the refusal points to the user's own Claude or ChatGPT through the plugin at https://github.com/SCORELabUS/sphere-orbit-plugin (`ORBIT_SKILL_URL` overrides it; set empty, the refusal points to the MCP server, which has no such limit since it calls no model).
- A conversation is one MongoDB document (16 MB cap, files included): new messages are refused with 409 past 12 MB, or 4 MB of files.
- Phase 2 (teams and permissions) adds role changes, removals, invitation revocations, moves, ownership transfer and pricing/collection permissions, plus the `list_resources`, `who_can_access` and `get_member_access` review tools. Role changes and removals act on the direct membership; an inherited role is changed in the parent. Revocations are checked against the organization's own invitations, because `OrganizationService.revokeInvitation` accepts any id.
- An ownership transfer goes alone in its plan, which stores a `confirmationPhrase` (the organization's name); `POST /orbit/plans/:id/confirm` needs it back in `confirmation`.
- Phase 3 (pricings and collections) lives in `orbitPricingTools.ts` (read tools), `orbitPricingSteps.ts` (plan validation, with the same `PermissionEngine` checks the API makes) and `orbitPricingDiff.ts` (version comparison). Executed steps call `PricingService`/`PricingCollectionService`, which check permissions again. Pricing YAML is always parsed from text with `retrievePricingFromText`: `retrievePricingFromPath` can rewrite the file it reads.
- Phase 4 (account and notifications) lives in `orbitAccountTools.ts` (read tools) and `orbitAccountSteps.ts` (plan validation). It only touches the user's own notifications, notification preferences and public profile, through `NotificationService` and `UserSettingsService`; social links are checked with the same `isValidSocialUrl` as the settings endpoint.
- Phase 5 (deletions) lives in `orbitDeletionSteps.ts`. A deletion plan holds nothing else and stores a `confirmationPhrase` (the name of what goes, or `delete N items`). Deleting an organization takes being its OWNER and deletes its whole tree, deepest first, because `OrganizationService.destroy` checks no permissions and leaves sub-organizations behind; the run fails if the tree changed after the plan.
- Phase 6 (MCP) lives in `OrbitMcpService.ts` and is served at `POST /api/v1/orbit/mcp` with the official SDK (`@modelcontextprotocol/sdk`, stateless Streamable HTTP). It only takes user API keys (`x-api-key`) and calls no language model: it runs ORBIT's tools through `OrbitToolRunner.runParsed`, leaves `propose_plan` plans in a conversation with `channel: 'mcp'` (plan `source: 'mcp'`, with the `apiKeyId` that proposed it). `confirm_plan` applies a plan only with that same key, through `OrbitService.confirmPlan` (phrase, daily allowance and confirmation limit as in the web). An `initialize` opens a session (in memory, bound to the user and the key, closed after 30 idle minutes, answers as SSE); when the client supports elicitation, SPHERE asks the user in a dialog the model cannot answer, and the phrase of deletions and handovers is typed there. Requests without a session stay stateless and answer in JSON; then the assistant's call confirms, with the phrase the user typed. Plans can still be confirmed in the web. The key's scopes bound every organization named in the arguments and filter `list_my_organizations` and `search_pricings`: VIEW only reads, and ownership transfer, moves and organization deletions need ALL. The tools also read with the key, as the REST API does (`OrbitActor.apiKey`, applied by `resolveOrgRole` and by the services through `requesterOf`): a VIEW scope acts as a plain MEMBER, MANAGEMENT at most as an ADMIN, and a global ADMIN gets no bypass, so private versions and private collections only reach the assistant where the key's user may read them as such. For an assistant that needs private reads without write power, use a dedicated member account granted GET on the specific pricings or collections, with a VIEW key of that account (or a MANAGEMENT key if write power is acceptable).
- Private versions and private collections are read by one rule, `policies/privateReadRule.ts` (`PermissionService.privateReader` / `canReadPrivateVersions`, first written for private permanent links): OWNER/ADMIN of the organization, a global ADMIN with a token, or GET on the pricing or its collection (or on the collection), with API keys limited as above. Listings, show, configuration space, forks, follows and their notifications, ZIP downloads, write responses, permissions endpoints and ORBIT use it; a pricing whose versions are all private answers like a missing one to anyone else. Permissions in listings are matched by organization and slug (`pricingKeys`, `collectionKeys`), never by slug alone.
- New operations for later phases are added as tools in `OrbitTools.ts`, plan operations in `types/models/Orbit.ts`, validation in `OrbitPlanService` and execution in `OrbitExecutorService`.

## MCP OAuth

- `OAuthService` implements the MCP SDK OAuth provider; `OAuthRoutes` mounts the SDK protocol handlers under `/api/v1/oauth`. DCR is supported; CIMD is not advertised or fetched.
- `OAUTH_ISSUER_URL` overrides the public origin (otherwise `FRONTEND_URL`, then `http://localhost:5173`). The issuer must match the externally reachable origin; discovery is served at `/.well-known/oauth-authorization-server` and both root/path-specific protected-resource URLs. nginx and Vite proxy these documents to the API.
- OAuth is only accepted by `/orbit/mcp`: opaque `sph_oat_` access tokens live for one hour; rotating `sph_ort_` refresh tokens live for 30 days. Mongo stores hashes only, checks grant revocation on every request and retains spent refresh hashes until expiry to detect replay. Redis stores consent requests (10 minutes) and authorization codes (5 minutes), consumed atomically. The grant (the "connected application") is only created when its code is exchanged, so an approval whose code is never used leaves nothing behind.
- `/oauth/requests/*` and `/oauth/grants*` require a SPHERE web session, never an API key or OAuth token. Consent selects organization scopes with the shared selectors in `modules/core/components`. `/oauth/consent` preserves its request across password and SSO login in sessionStorage. Settings → Connected applications groups Claude and ChatGPT/Codex authorizations, offers OAuth setup guides, and edits or revokes each connection. `PUT /oauth/grants/:grantId` replaces the owner's active grant scopes with the same membership validation as consent, without rotating tokens or extending expiry; existing MCP sessions take the new scopes on their next request. Client-name grouping is display-only, not a verified application identity.
- MCP plans use namespaced `credentialId` (`oauth:<grantId>` or `api-key:<keyId>`); legacy `apiKeyId` plans remain confirmable by their original API key. Both credentials share the same MCP scopes and per-user rate limiter.
- No clients, grants or tokens are seeded; the seeder initializes the empty indexed OAuth collections. Run migration `20261024120000-create-oauth-collections` for existing databases.
- `/api/src/test/oauth.test.ts` covers discovery, DCR, PKCE, audience binding, single-use codes, refresh replay, consent ownership, grant revocation and MCP credential isolation. Run integration tests only against `DATABASE_NAME=sphere_scratch`, Mongo 27018 and Redis 6378: the shared test harness drops its selected database.

## Organization services (beta)

- An organization's Services tab (beta feature `organization-services`) shows the services it offers as a tree, like Helena's: each service is autonomous ("Aut"), dependent ("Dep", on the provider's functionality or on an account) or of any kind the organization makes up (`kind` and `dependency` are free text of up to 40 characters; the known values are stored in capitals, and empty means not classified), and links pricings of the organization by `pricingId`, so links survive renames and collection moves.
- One `serviceTrees` document per organization (`ServiceTreeMongoose`, migration `20261104120000-create-service-trees`), a flat list of nodes with `parentId`; siblings keep the list order. `GET /orgs/:id/services` is for members, `PUT` (OWNER/ADMIN) replaces the whole tree with the `revision` it was based on (409 if stale). `ServiceTreeService` validates ids, parents, cycles, depth and sizes, and that linked pricings are live pricings of the organization; organizations deleted through `OrganizationService.destroy` take their tree with them.
- Linked pricings are named through the organization's pricing listing with the caller's permissions (which returns `pricingId`), so a member never sees the name of a pricing they cannot list; they only see how many are hidden.
- View mode (everyone; the only mode for members) shows the tree on the left and the picked service on the right (`ServiceDetail`, read-only). OWNER/ADMIN also get Edit, with two shapes: Tree, an outline (`ServiceOutline`) where names are typed in place, the type is picked from the row (`KindPicker`), details and pricings open under the row, and services nest with Enter/Tab/Shift+Tab/Alt+arrows, the row menu (including Move to…) or dragging; and JSON. Edit mode works on a local copy with undo/redo (Ctrl+Z, Ctrl+Shift+Z, also while typing a name); `components/services/tree.ts` holds the pure tree operations. It saves in one go, leaving the tab with unsaved changes asks first, and it marks what was added, changed and removed since the last save (`diffTrees`).
- The JSON shape shows the same tree as JSON text (`services/treeJson.ts`): nested `services`, lowercase `kind`/`dependency`, `pricings` by slug (pricingId when a slug is ambiguous or unknown). Every valid change of the text reaches the tree at once; errors keep the last valid tree and block saving.
- Each service has `interfaces`, the ways it is used, shown like Helena: an "Interfaces N +M pending" group under the service in the tree, with each interface's channel tag (Int, Prog, Conv, Agent, Event), and an Interfaces tab of cards by channel in its details; Edit has an Interfaces panel in each row. An interface has `name`, `channel` (free text; the known ones in capitals), `pending`, `description` and `mechanisms`, and keeps any other field (e.g. `quote` with its `source`, shown as a quote with its link). The taxonomy lives in `services/interfaces.ts`: a new channel is one entry in `CHANNELS`, an unlisted channel still shows with its own name, and new fields show in the cards without code changes. The tree's "Pricing" row reads "N plans · M add-ons" from the linked pricing's analytics (`plans`/`addOns` in the response).
- Each service also has `links`, pages that answer questions about its terms (refunds, cancellation, SLA...): `url` (absolute http/https only, checked in `ServiceTreeService.parseLinks` and in `services/links.ts`), `title`, `topic` (free text, kept as written) and `description`, plus any other field, kept like an interface's. The tree shows a "Links N" group under the service, its details have a Links tab grouped by topic (opened in a new tab with `rel="noreferrer noopener"`), and Edit has a Links panel in each row (`LinkEditor`); Save waits until every link has a valid address.
- Any other key of a service in the JSON is a free attribute, stored in the node's `attributes` (validated in `ServiceTreeService.parseAttributes`, names in `RESERVED_ATTRIBUTES` refused) and listed in its details. A new kind of data (e.g. `customers`) can start there with no schema change; give it a field and UI of its own only when it needs one.

## Pricing version graph and forks

- A fork always creates a new pricing (`POST /pricing-forks`), whose first version stores `forkedFrom` (source pricingId, organization, slug, name and version label). A version is never forked into a pricing that already exists: bringing a fork's changes back to the pricing it came from is a pull request (see Pricing pull requests).
- `GET /pricing-graphs/:org/:slug` (`PricingService.graph`) returns the pricing's lane and the lane of the pricing it was forked from (`source`); the forks made of a pricing are never drawn. Each lane is read through `show()`, so private versions, hidden collections and unreadable pricings follow the same rules; an unreadable source keeps a lane with `available: false` and only the label its fork names. Older data whose later versions name origins draws those too (at most 20). It lives outside `/pricings/**` so it cannot clash with a version named "graph".
- Frontend: the Versions tab of a pricing shows `components/pricing-version-graph` (lanes with sticky names, versions in insertion order, a branch from the origin to the fork's first version). From 13 versions on, runs of versions no branch touches fold into "+N" gaps, long links stay thin until one end is picked or hovered, and the view scrolls inside a capped height. The pure layout (folding, lane order, routing) is in `utils/version-graph.ts`, tested in `frontend/test/version-graph.test.ts`.
- Pointing at (or focusing) a dot of the graph opens a card with what that version changed (`pricing-version-graph/change-summary-card.tsx`): plans, features, add-ons and usage limits added (+), removed (−) or changed (~), the plans and add-ons whose price moved, and other fields. It compares the version with the one it was forked from, or with the version of its lane added before it (`baseVersionOf`), reading both YAML files (each graph version carries its `yaml` URL) through the comparator's `diffPricings`; `utils/change-summary.ts` turns that diff into the summary, tested in `frontend/test/change-summary.test.ts`. A first version lists what it starts with.
- Version order: a version's `createdAt` comes from its YAML (a day, or a date-time) and can tie, so each version also stores `addedAt`, the instant SPHERE received it. `PricingRepository.create` sets it on every insert (editor, upload, ZIP, fork, ORBIT), it is `immutable` and no request field reaches it. Every listing orders newest first by `addedAt`, then `_id` (`utils/version-order.ts`: `VERSION_ORDER` for queries, `compareVersionsNewestFirst` in code); the graph and the Versions tab use the same insertion order; `createdAt` is release metadata only. Migration `20261106120000-pricing-added-at` (also run by the seeder) fills older versions from their `_id` timestamp.

## Pricing pull requests

- A pull request proposes a new version of a pricing P without publishing anything; only a maintainer's merge publishes. One `pricingPullRequests` document each (`PricingPullRequestMongoose`, migration `20261111120000-create-pricing-pull-requests`, also run by the seeder, which leaves it empty), numbered `#N` per pricing. Served under `/api/v1/pricing-pull-requests` (`PricingPullRequestRoutes`), outside `/pricings/**` like `/pricing-forks`: there the middleware would ask CREATE or PUT of whoever only proposes, and a version named "pull-requests" would clash. So the middleware checks neither membership nor entity permissions, and `PricingPullRequestService` checks them all. Only web sessions get in: an API key gets 401 `WEB_SESSION_REQUIRED`, and OAuth tokens are refused before. Errors answer `{ error, code }` (`PullRequestError`, codes in `types/models/PricingPullRequest.ts`). ORBIT and the MCP server do not touch pull requests; the service takes the user explicitly, so a later phase can add tools for them.
- Routes: `GET /?pricingId=&status=&page=` (20 a page, with `counts` by status and `proposals { canOpen, reason, latest }`), `GET /fork-target?forkPricingId=`, `POST /previews` (computes a merge and writes nothing), `POST /` (`source.kind` `text` or `fork`), `GET /:id`, `PUT /:id` (title, description, `proposedYaml`), `POST /:id/merge-preview` (`purpose` `update` or `merge`), `POST /:id/update`, `POST /:id/merge` and `POST /:id/close`. The contract and the order of the errors are in the OpenAPI spec.
- Who: a reader of P is anyone when P has a public version, or else who may read its private versions (`canReadPrivateVersions`). A maintainer has CREATE on P (`PermissionEngine`, as `createVersion`) and, if P has private versions, reads them; a global ADMIN is one, but is only notified as a member. A pull request is shown to its author while they are still a reader, and to the maintainers; anyone else gets 404, and in the list sees only their own (with the counts of those). Only the author edits, updates or withdraws it (`closed.kind: withdrawn`); only a maintainer merges or rejects it (`rejected`, with an optional `reason`). Reopening, comments and choosing who may open pull requests do not exist yet.
- Public base: every pull request starts from the latest public version of P by `VERSION_ORDER`, for everyone, and stores a copy of its YAML (`base.yaml`). A text proposal (editor or uploaded YAML) names that version as `baseVersionId`, or gets 409 `BASE_NOT_LATEST` with `latest`; one that changes nothing gets 400 `NO_CHANGES`. P without a public version answers `NO_PUBLIC_VERSION` to who reads its private versions and 404 to anyone else. The author may change `proposedYaml` only while the base is still the latest public version (409 `PULL_REQUEST_BEHIND`), and not to its base (400 `NO_CHANGES`); `POST /:id/update` brings it up to that version through the resolver (409 `PULL_REQUEST_UP_TO_DATE` if it already is). The state (`merged`, `closed`, `no-public-version`, `up-to-date`, `no-changes`, or `behind` with its conflicts) compares with the latest version for a maintainer and with the latest public one for anyone else; `no-changes` (merging adds nothing, also after an update) wins over `up-to-date` and takes away `permissions.merge`. Nothing that reaches a caller who may not read P's private versions (answers, `merged.versionId`/`version`, `origin`, `suggestedVersion`, which is the proposal's own `version:`, notifications) names, counts or quotes a private version.
- Fork: `fork-target` and `source.kind: fork` propose the newest version of F the caller may read (as `show()` decides) to P, the `forkedFrom.pricingId` of the newest readable version of F that names one. It takes CREATE on F (403); otherwise `NOT_A_FORK` (422), and `PARENT_UNAVAILABLE` (404) alike for a deleted or an unreadable P. It is a three-way merge of a base, the latest public version of P and the proposal. The base is the version of F that the latest merged pull request from F proposed, while F keeps it (the common ancestor, so what a maintainer kept or removed does not come back); otherwise the newest version of F copied from P. The preview warns `PREVIOUSLY_MERGED { number }` when a pull request from F was merged before. At most one pull request from F to P is open: its author's new proposal replaces it (200 `updated`, same number, `proposalRevision` + 1), anyone else's gets 409 `PULL_REQUEST_EXISTS { number }`. Proposals for the same F and P queue in `withPricingRevisionLock('pr-fork:<F>:<P>')`; a partial unique index is only defence in depth. The fork itself never changes, and nothing syncs a fork from its parent.
- Merge engine (`utils/pricing-merge.ts`, pure, no `fs`): plans, features, add-ons and usage limits are compared by name and field by field, and their order counts; the reference lists (`linkedFeatures`, `availableFor`, `dependsOn`, `excludes`) combine as sets; the rest of the file is the general section; `saasName`, `version` and `createdAt` are ignored. Each conflict (`value`, `entry`, `list` or `order`) carries base, current and proposal as YAML text (`present: false` when absent) and is resolved with `current` ("Keep current") or `proposal` ("Use proposal"); a `manualYaml` the user typed wins over the resolutions (`MANUAL_OVERRIDE`). A combined result is dumped again (`FORMAT_REGENERATED`). Every input (proposals, `manualYaml`, stored files) goes through `utils/pricing-syntax.ts`: at most `PRICING_PR_MAX_YAML_BYTES` for what the user sends and 5 MiB for stored files (413 `PRICING_TOO_LARGE`), a first load with `CORE_SCHEMA` and a budget that counts every use of an alias or `<<`, and the characters of every key and string on each use up to twice the byte limit (422 `PRICING_TOO_COMPLEX`), `__proto__`/`constructor`/`prototype` refused, then the parser's schema and an upgrade to syntax 3.1 with pricing4ts' updater (`SYNTAX_UPGRADED`). Proposals are stored in 3.1 with P's `saasName`, so publishing one never makes pricing4ts rewrite its file. Results are validated with `retrievePricingFromText`, never from a path.
- Preview tokens: every preview returns a `previewToken` (`serverHmac('pricing-pr-preview', ...)`, checked with `timingSafeEqual`) that names the caller, the subject and the base, target and proposal it was computed from; it does not expire. Submitting needs it: a newer public target gets 409 `BASE_NOT_LATEST` (on a merge, any newer version gets `PREVIEW_STALE` "There is a newer version than the one you reviewed"), and anything else that changed, the pull request's `proposalRevision` included, gets 409 `PREVIEW_STALE`.
- Merge: `POST /:id/merge` publishes through `PricingService.createVersion` (CREATE, unique label, analytics, the followers' `PricingUpdated` and the revision claim), passing `mergedFrom: { number, prId }`, which only the server sets. The label (`version`) and the visibility (`private`, by default that of the latest version) are the maintainer's choice; `saasName`, `version` and `createdAt` (now) are stamped line by line (`utils/pricing-top-level.ts`), and the rest of the text is published as reviewed. Only then is a file written, to `static/pricings/uploaded/<org>/<slug>/<label>-pr-<time>-<uuid>.yml` (`writeUploadedPricingFile`, `wx`).
- Concurrency: the merge reads the revision and the latest version of P under `withPricingRevisionLock`, releases it (the queue is not reentrant and `createVersion` takes it again) and publishes with a server-built precondition on that revision, so a version published meanwhile makes it 409 `PRICING_CHANGED_DURING_MERGE`. The client's own `If-Match` is checked as well (412, with `ETag` only for who reads private versions, as elsewhere). The pull request is reserved first (`mergeLock`, 10 minutes, on `status: open` and the reviewed `proposalRevision`): while it holds, `PUT`, `update`, `close` and fork proposals get 409 `PULL_REQUEST_MERGING`, and a second merge never publishes twice. If the publish fails, the reservation and the file go; once the version exists its file stays, and a merge that stopped before marking the pull request merged is finished on its next load (`reconcileMerge`, from the version whose `mergedFrom.prId` names it). The pull request writes never move the pricing's ETag; only the merged version does. Like the rest of the revision queue, this assumes a single API process.
- Versions and graph: a merged version stores only `mergedFrom { number, prId }`, which show, listings and permanent links return as such. `GET /pricing-graphs` adds `mergedFrom.from` (the fork's pricingId, name, slug and organization) only for who may read the fork, and `null` when the author edited the proposal by hand; a merge draws no lane.
- Notifications: kind `PricingPullRequest`, by inbox and email, both on by default and switchable in Settings → Notifications. Opening one tells the maintainers who are members of P's organization or of its ancestors (OWNER, ADMIN, MEMBER, then by user id; at most 50; never the author); a fork proposal that replaces an open one tells them again at most once every 24 hours (`lastNotifiedAt`). Merging or rejecting tells the author unless they did it, without the label if they may not read the merged version. Titles carry no text a user wrote.
- Limits and variables: `PRICING_PR_MAX_OPEN_PER_AUTHOR` (open ones per author and pricing, 5), `PRICING_PR_MAX_OPEN_PER_PRICING` (50) and `PRICING_PR_MAX_CREATED_PER_DAY` (per author over the last 24 hours, 20) answer 429 `LIMIT_REACHED` before anything is parsed (only a maintainer is told which one); replacing one's own fork proposal does not count. `PRICING_PR_MAX_YAML_BYTES` defaults to 1048576 and never goes above it (a JSON body takes at most 2 MB and escaping can almost double a text). The `pricing-pr` limiter (counters in Redis per user) covers `POST /`, `/previews`, `/:id/merge-preview`, `/:id/update` and `/:id/merge` with `PRICING_PR_RATE_LIMIT_MAX_REQUESTS` (20) every `PRICING_PR_RATE_LIMIT_WINDOW_SECONDS` (60); 0 turns it off, and it is off under Vitest unless set. The states of the list are cached in memory (500 entries, by pull request, proposal revision, base and target).
- Storage and deletions: each pull request keeps a copy of its base YAML and its proposal in MongoDB (in practice at most about 2 MiB and 1 MiB), and nothing removes old ones yet, so the worst case is about 60 MiB a day per author. When `refreshIdentities` marks a pricing deleted (its last version went, through `destroy`, a version deletion, a deleted collection or a deleted organization), its pull requests are deleted with it. A deleted fork leaves its pull requests mergeable without `origin`; a deleted author leaves them mergeable with `author: null`.

## Collection PUT authority

- A pricing inside a collection uses that collection's PUT permission for edits, including version visibility; individual PUT cannot override the collection. Existing GET/privacy and DELETE rules remain unchanged.
- Entering or leaving a collection requires independent PUT on the pricing and PUT on each affected existing collection (both source and destination for moves). Inherited PUT is not enough for membership changes. Creating a collection with existing pricings follows the same rule.
- `PermissionService.checkPricingPut` and `assertPricingMove` resolve actual stored membership and credential scopes; query parameters never supply authority. REST, the permissions returned to the UI and ORBIT/MCP plan validation use these checks. VIEW credentials remain read-only.
- `api/src/test/collection-put.test.ts` and `api/src/test/unit-tests/collection-put-permissions.test.ts` cover inheritance, denied overrides, membership moves, permissions reported to the UI and credential scopes.

## Instructions for Adding New API Endpoints

1. Define the endpoint in the OpenAPI spec (`/api/docs/sphere-api-docs.yaml`). This will serve as the source of truth for the endpoint's contract, including request/response schemas and authentication requirements.
2. Implement the endpoint in its corresponder router (different routets can be found in `api/src/main/routers/`). Follow the RESTful conventions to name the endpoints and ensure that the implementation adheres to the contract defined in the OpenAPI spec.
3. Add any necessary permissions of the endpoint in `api/src/main/config/permissions.ts`. This will ensure that the endpoint is properly secured and only accessible to authorized users.
4. Add a method in the appropiate controller (found in `api/src/main/controllers/`) to parse the request body and parameters to the appropriate data structures. The controller should interact with the necessary services to fulfill the request and return the appropriate response.
5. If needed, add any necessary business logic in the services layer (found in `api/src/main/services/`). This layer should contain the core logic of the application and should be decoupled from the controllers and routers to ensure separation of concerns. If needed, you can use repositories here to communicate with the database. Nontheless, if you can fulfill the requirements of the endpoint without adding any new logic to the services layer, you can directly call the necessary service methods from the controller.
6. If the endpoint requires any changes to persist in the database or requires retrieving information from it, add any necessary database queries in the appropriate repository (found in `api/src/main/repositories/mongoose/`).
7. Write tests for the new endpoint in the appropriate test file under `api/src/test/
8. Ensure that the tests cover various scenarios, including successful requests, validation errors, and unauthorized access. Use the test utilities in `api/src/test/utils/` to help set up test data and mock dependencies as needed.
9. Run the tests to verify that the new endpoint works as expected and does not introduce any regressions. Use `pnpm run test` from the root directory to execute all tests, or run specific tests using `npx vitest --run --test-name-pattern "<pattern>"` from the `api` directory.

IMPORTANT NOTES if adding a new entity to the database schema:

- You must create a new mongoose schema in `api/src/main/repositories/mongoose/models`
- You must add any necessary migrations in `api/src/main/migrations/`. Remember to run the migrations using `npx migrate up` after implementing the new endpoint to ensure that the database schema is updated accordingly.
- You must update the seeders located in `api/src/main/database/seeders/mongo/` to reflect the changes
- You must register the new repository and service in the awilix container located in `api/src/main/config/container.ts` to ensure that they can be properly injected into the controllers and other services as needed.

## Instructions for Adding New Frontend Pages/Components

The frontend organizes its functionality in modules, which are located in `frontend/src/modules/`. Each module corresponds to a specific feature or section of the application and contains its own components, pages, and styles. When adding new pages or components, you should determine which module they belong to based on their functionality and the existing structure of the application. In particular, each module may have the following subfolders:

- pages/: contains the main pages of the module, which are typically associated with specific routes in the application. Pages are responsible for rendering the overall layout and structure of a particular section of the application and may include multiple components to display data and handle user interactions.
- components/: contains reusable components that are specific to the module. These components can be used across different pages within the same module and are designed to encapsulate specific functionality or UI elements related to the module's feature set. IMPORTANT: If you wanna reuse a component across different modules, you should place it in the `frontend/src/modules/core/components/` folder instead of the module's components folder.
- utils/: contains utility functions that are specific to the module. These functions can be used across different components and pages within the same module and are designed to encapsulate specific logic related to the module's feature set. IMPORTANT: If you wanna reuse a utility function across different modules, you should place it in the `frontend/src/modules/core/utils/` folder instead of the module's utils folder.
- api/: contains functions that handle API calls related to the module's feature set. These functions are responsible for making HTTP requests to the backend API and processing the responses. They can be used across different components and pages within the same module to interact with the backend and retrieve or manipulate data as needed. IMPORTANT: remember to check wheter an API function that fulfills your needs already exists before creating a new one, even in a different module. If it does, you should reuse it instead of creating a new one.
- contexts/: contains React contexts that are specific to the module. These contexts can be used to manage state and share data across different components and pages within the same module. They are designed to encapsulate specific logic related to the module's feature set and can help improve the organization and maintainability of the codebase.
- hooks/: contains custom React hooks that are specific to the module. These hooks can be used to encapsulate reusable logic related to the module's feature set and can help improve the organization and maintainability of the codebase. They can be used across different components and pages within the same module to handle common functionality such as form handling, data fetching, or state management.
- layouts/: contains layout components that are specific to the module. These components are responsible for defining the overall structure and layout of the pages within the module and can be used to ensure a consistent look and feel across different sections of the application.

When adding new pages or components you should always follow the style depicted in `./DESIGN.md` and make sure to keep the code organized and maintainable by placing it in the appropriate module and subfolder based on its functionality and purpose. Additionally, remember to update the routing configuration if you are adding new pages that need to be accessible via specific routes in the application.

If you need to add any new color to the palette, you should add it to the `frontend/src/main/styles/tailwind.css` file to ensure that it can be used consistently across the application and is available for use in the TailwindCSS classes throughout the codebase. In addition, you should ALWAYS include a dark mode variant for any new colors you add by extending the class `.dark` in the same file. This will ensure that the new colors are properly displayed in both light and dark modes, providing a better user experience for users who prefer dark mode.

IMPORTANT RULE: EVERY CLICKABLE COMPONENT IN THE UI MUST HAVE A "cursor-pointer" CLASS TO INDICATE THAT IT IS INTERACTIVE. This is a crucial aspect of the user experience, as it provides a visual cue to users that an element is clickable and can be interacted with. By adding the "cursor-pointer" class to all clickable components, you can improve the usability of the application and make it more intuitive for users to navigate and interact with the various features and functionalities available.

## SCORETech Identity sign-in

- `AUTH_PROVIDER=local|scoretech` defaults to local. Native development sets it
  in the API environment; production Compose takes it from `docker/production/.env`
  and passes it explicitly to both API and Nginx. The frontend reads `/auth/config`;
  do not introduce a second Vite mode switch.
- Identity gateway routing is generated by `nginx/production/15-scoretech-mode.sh`.
  `SCORETECH_IDENTITY_PREVIEW=true` exposes `/identity` during setup while local
  authentication and the US callback remain on SPHERE. In Identity mode only the
  legacy US callback moves to Identity; `/api/v1/auth/identity/callback` always stays
  on SPHERE. Preserve path/query encoding, sanitized forwarding headers, Docker
  DNS re-resolution and private native-route blocks.
- `node nginx/production/test-gateway.mjs` uses isolated synthetic Docker upstreams
  and the sibling Identity production gateway configuration. It calls no providers
  and removes only its temporary project.
- `ScoretechIdentityService` owns the confidential OIDC code/PKCE/nonce flow,
  browser-bound one-use state and private Redis refresh sessions. Credentials
  never go into browser config, tokens in redirect URLs or public cache entries.
- Identity-mode SPHERE JWTs carry `identitySessionId`; API, static and SSE reads
  enforce the live bridge. Preserve native refresh rotation, same-user renewal,
  outage recovery and logout-versus-refresh exclusion. Reject legacy local web
  tokens in this mode; keep API-key/MCP scopes independent.
- Existing accounts link explicitly from local Settings → Account before the
  switch. Never auto-merge SCORETech identities by email or copy central roles
  into SPHERE's ADMIN. Preserve account IDs, local credentials and memberships.
- Hide shared profile/social/security settings in Identity mode, expose the
  central profile in a new tab, and keep service-specific settings and SPHERE-only
  deletion. Direct API writes enforce the same ownership boundary.
- `docs/scoretech-identity.md` and `api/.env.scoretech.example` describe setup and
  rollback. `pnpm --dir api run test:e2e:identity` is separate from the ordinary
  browser suite; it needs the sibling Identity lab and the isolated scratch DB.
